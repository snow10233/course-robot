## 11. 排程機制：Linux 有什麼、我們用什麼

Linux 沒有單一的「內建計時器」，而是有幾套機制，取決於系統：

| 機制 | 說明 | 是否適合我們 |
|---|---|---|
| **systemd timer** | 由 systemd（大多數發行版的 init）提供，`deploy/systemd/course-robot.timer` 就是這個 | 適合，但需要 systemd 且要修現有問題（使用者未建立、間隔 30 分鐘、`run-sync.sh` 不帶 `--calendar`） |
| **cron** | `cron` 套件提供；WSL 與多數 VPS 預設**不一定啟動** | 可用，但在容器裡要額外跑 cron daemon，較麻煩 |
| **容器內 sleep 迴圈** | 程式自己算「距離下一個 00:00 還有幾秒」再睡 | **我們的選擇**：自帶排程、不依賴宿主 |

**決定：容器內建排程。** 這樣 `deploy/calendar/compose.yaml` 完全自足——不需要宿主設定 cron、不需要 systemd，換一台 VPS 也能直接跑。

實作要點：

```
啟動 → 先執行一次（可選）→ 算出下一個 00:00（Asia/Taipei）→ sleep 到那個時間 → 執行 → 重複
```

- 重啟後會**立刻補跑一次**，所以 VPS 重開機也不會漏掉當天的同步。
- `deploy/systemd/` 保留但不作為主要路徑；若你之後偏好宿主排程，修好上面三個問題即可使用。

## 13. 環境變數覆蓋問題（實際踩到）

**症狀**：`.env` 已改成新日曆 ID，但 `calendar-check` 一直回 404；直接讀 `.env` 卻是新值。

**原因**：`config.py:27` 用 `load_dotenv(root / ".env", encoding="utf-8-sig")`，而 python-dotenv 預設 **`override=False`**——**已存在的環境變數優先**。當時 shell 裡有舊的 `GOOGLE_CALENDAR_ID`，所以 `.env` 的新值完全沒生效。

```
shell 環境變數 : GOOGLE_CALENDAR_ID=dbd1cff3…（舊）   ← 勝出
.env 檔案      : GOOGLE_CALENDAR_ID=30406415…（新）   ← 被忽略
```

**影響**：任何「改 `.env` 卻沒生效」的情況都會變成極難診斷的錯誤，而且症狀會誤導人往權限方向查。這在 VPS 上更危險——容器環境變數會蓋掉掛載的 `.env`。

**修法**：改為 `load_dotenv(root / ".env", encoding="utf-8-sig", override=True)`，讓 `.env` 成為唯一來源。

**當下繞過方式**：在 shell 裡 `unset GOOGLE_CALENDAR_ID` 後再執行。

## 12. 後端 API 的輸出形式

### 12.1 共同約定

- **格式：JSON**（`Content-Type: application/json; charset=utf-8`）
- **時間：ISO 8601 含 `+08:00` 位移**（與資料庫、事件格式一致）
- **認證：`Authorization: Bearer <BACKEND_API_TOKEN>`**；`/healthz` 不需要
- **CORS**：只允許前端網域（未來 Web UI 用）
- **快取**：回應帶 `ETag`（內容雜湊），支援 `If-None-Match` → 304

### 12.2 端點

**`GET /api/courses`** — 目前窗口內的課程

```json
{
  "data": [
    {
      "source_id": "558798",
      "start_at": "2026-09-18T14:00:00+08:00",
      "end_at": "2026-09-18T14:30:00+08:00",
      "student_name": "郭尚儒",
      "grade": "小四上",
      "chapter": "乘法_1B",
      "class_type": "1v1",
      "room_id": "R2026091800298",
      "class_url": "",
      "preview_pdf_name": "小四上_第二章_乘法_1B(學習教材)",
      "preview_pdf_url": "https://files.peak1.com.tw/…",
      "answer_pdf_name": "小四上_第二章_乘法_1B(學習教材解答)",
      "answer_pdf_url": "https://files.peak1.com.tw/…"
    }
  ],
  "meta": {
    "fetched_at": "2026-09-16T00:00:03+08:00",
    "window_start": "2026-09-04T14:00:00+08:00",
    "window_end": "2026-09-27T20:00:00+08:00",
    "count": 84
  }
}
```

- **不含 `student_id`**（`models.to_public_dict()` 定義的公開欄位就是這些）
- 支援可選 `?from=YYYY-MM-DD&to=YYYY-MM-DD` 過濾
- 沿用老師站既有的 `{data, meta}` 信封，與前端習慣一致

**`GET /api/status`** — 服務狀態

```json
{
  "data": {
    "last_fetch_at": "2026-09-16T00:00:03+08:00",
    "last_fetch_ok": true,
    "last_error": "",
    "window_end": "2026-09-27T20:00:00+08:00",
    "course_count": 84
  }
}
```

**`GET /healthz`** — 給容器 healthcheck 用，不需認證

```json
{"status": "ok", "last_fetch_age_seconds": 312}
```

### 12.3 錯誤格式

```json
{"error": {"code": "upstream_unavailable", "message": "老師站回應逾時"}}
```

| HTTP | `code` | 情境 |
|---|---|---|
| 400 | `bad_request` | `from`／`to` 格式錯誤 |
| 401 | `unauthorized` | token 缺少或錯誤 |
| 502 | `upstream_unavailable` | 老師站連線失敗 |
| 503 | `upstream_invalid` | 老師站回應不完整（分頁驗證失敗） |

**關鍵：分頁驗證失敗時回 503，不回不完整的資料。** 這樣 Calendar 服務會整輪中止，不會拿殘缺清單去刪日曆。

### 12.4 Calendar 服務怎麼用它

```
GET /api/courses  →  data（課程清單）+ meta.window_end
   → 若 HTTP 非 200 或 data 為空 → 本輪中止，不執行任何刪除
   → 否則列舉日曆、比對、寫入
```

## 14. 實作完成後的已知限制（2026-09-16）

### 14.1 已刪除的事件 ID 是永久保留碼

實測確認 Google 的行為：

| 操作 | 結果 |
|---|---|
| `POST` 一個曾被刪除的 ID | `409 The requested identifier already exists` |
| `PATCH` 同一個 ID | `200`，但回傳的事件 `status = cancelled`（不會復活） |
| `GET` 該 ID | `200`，`status = cancelled` |
| `events.list`（`showDeleted=false`） | **看不到**（與一般事件無異） |
| `DELETE` 該 ID（想徹底清除） | `410`，清不掉 |

程式已處理：清單看不到的 ID 不再嘗試 PATCH，改用由內容推導的替代 ID。

### 14.2 事件 ID 的合法字元比文件更嚴

實測 `w`、`x`、`y`、`z` **也會被拒**（`400 Invalid resource id value`），雖然它們看起來像合法字母。產生 ID 時已排除，並有測試覆蓋。

### 14.3 已解決：正規 ID 為保留碼時的每輪重建（2026-09-16）

**症狀**：正規 ID 是保留碼時，每輪建立新的替代 ID 事件、再刪掉上一輪那個，不收斂。

**修法**（已實作）：
1. `build_plan` 計算「這堂課的 ID 集合」時，除了正規 ID，也納入由內容推導的替代 ID 候選，因此上一輪建立的替代 ID 會被認出、走更新而非重建。
2. `_place_create` 一律**驗證事件實際落點**：`patch_event`／`insert_event` 內建的 404↔409 互相補救可能把事件放到別的 ID 上，落點不符就換下一個候選。

## 15. 課時規則（2026-09-16 變更）

### 15.1 現行規則

來源的「時段」比實際授課時間多 5 分鐘緩衝，換算只取決於該堂課自己的時段長度：

| 來源時段 | 日曆上顯示 | 說明文字 |
|---|---|---|
| 30 分鐘 | **25 分鐘** | `課時：25 分鐘（實際授課時間）` |
| 60 分鐘 | **50 分鐘** | `課時：50 分鐘（實際授課時間）` |
| 其他 | 時段 − 5 分鐘（最少 1 分鐘） | `課時：N 分鐘` |

實測（2026-09-16，50 筆）：42 筆 30 分鐘 → 25 分鐘；8 筆 60 分鐘 → 50 分鐘。日曆上的長度分布為 `{25: 42, 50: 8}`。

**這個換算只依賴單堂課自己的來源長度**，與其他課程無關，所以同一堂課永遠得到同一個結果——這是同步能收斂的必要條件（見 §15.2）。

### 15.2 為什麼顯示時間不能取決於「分組」

實作過程中曾嘗試讓「國小連續兩節」的第二節往前貼齊第一節的結束時間（讓兩場合計剛好 50 分鐘不中斷）。結果：**3 筆事件每一輪都被重寫，連續三輪都是「修改 3」**，永遠不收斂。

原因是事件內容雜湊必須能由單堂課重算；一旦顯示時間取決於「當次有沒有配到對」，同一堂課在不同計算路徑下會得到不同雜湊，系統就永遠認為它需要更新。

**若之後仍要做貼齊**：需要把「這堂課的配對夥伴」持久保存下來（一個小的狀態檔即可，不需要關聯式資料庫），讓雜湊由「單堂課 + 已保存的配對」決定。

> 也曾用「國小 + 分針為 30」推導連堂，誤標 42 筆（任何 14:30 開始的課都被誤判），該啟發法已移除。連堂的正確判斷需要看「同一學生前後兩堂是否相接」，不是看單一堂課的時間。
